# 「放置陪伴小屋」游戏 UI 三方向比稿报告

## 1. 模式与归一化 brief

- **模式**：Design / `ui-mockup`
- **目标**：基于同一张暮色书房底图，为双人放置陪伴 Web 应用探索三套真正不同、去 Discord 化的游戏 UI 骨架。
- **输出约束**：三张 1586×992 PNG；不出现可读中英文或数字；场景始终为主角；每版至少展示一个次级打开态。
- **共同功能基线**：角色点击聊天 + 常驻聊天入口、五类物件热点、可收起播放器、三房间切换、灯光/天气、设置与远期商店、presence 文案位、固定布局的模块控制器。
- **生成方式**：仅使用 Codex 内置 `image_gen`；两张输入图均作为 reference image 使用，没有覆盖源文件，也没有使用 CLI/API-key fallback。

## 3. 执行结论

**推荐 C「窄 rail 混合式」作为产品默认骨架，置信度中高。** 它最符合“开着就行”的长期常驻体验：系统入口有稳定肌肉记忆，但视觉占用远低于旧侧栏；三房间仍用场景缩略图而非频道文本；聊天双通道、单热点 hover、独立播放器和模块开关都能同时成立。

最佳落地不是纯 C，而是：**C 的 60px 固定 rail + B 的功能分组逻辑 + A 的场景边缘切房箭头**。A 适合后续提供“沉浸模式”；B 适合首登引导或触屏设备，但不宜成为桌面常驻的唯一骨架。

## 4. 概念矩阵

评分为 1–5，越高越好；实现成本一栏单独使用低/中/高，避免把成本方向混淆。

| 方向 | 设计假设 | 沉浸感 | 可发现性 | 触达效率 | 多场景兼容 | 实现成本 | 总体判断 |
|---|---|---:|---:|---:|---:|---|---|
| A 极简融入式 | 用户愿意通过角色与物件探索；口袋只做兜底 | 5 | 3 | 3 | 4 | 高 | 最有游戏感，但首次学习与展开态密度风险最大 |
| B 悬浮胶囊式 | 高频动作可被收敛到一个稳定、优雅的操作面 | 4 | 5 | 5 | 5 | 中 | 最易上手，信息组织最佳；需控制任务栏感 |
| C 窄 rail 混合式 | 常驻系统入口能换来肌肉记忆，场景功能仍留在物件上 | 4 | 4 | 4 | 5 | 中低 | 综合最稳，最接近可工程化的长期产品骨架 |

## 5. 详细发现

### A — 极简融入式 / Pocket Radial

**可见证据**

- 场景无固定边栏；左右边缘仅保留柔和箭头，默认视觉最接近完整插画。
- 右下口袋处于展开态，功能按钮沿弧线散开；三房间缩略图、灯光与天气双排选择、聊天未读点、音乐与系统按钮集中在同一区域。
- 日记本上方只出现一组柔光 affordance；其他相框、挂钟、唱片机、许愿罐没有同时套上高亮圈。
- 聊天卡锚定粉耳角色附近，两张角色脸均未被遮住；左下播放器与左上模块示例卡验证了次级层级。

**优势**

- 默认态最沉浸，叙事关系清楚：角色与物件是主要入口，UI 只是兜底。
- 房间边缘箭头像“走到隔壁”，比列表切换更符合小屋世界观。
- 口袋打开具有明显游戏菜单仪式感，适合手柄/触屏式大目标。

**风险与具体修正**

- 展开态右下形成高密度工具花束，按钮层级依赖图标记忆。实现时把第一圈限制为聊天、音乐、房间、氛围四个高频项，其余进入第二级“更多”。
- 初次用户可能不知道物件可点。首次进入时只对一个推荐物件做 1.5 秒低频提示，此后改为 hover/focus 才显现。
- 扇形菜单碰撞检测、不同 viewport 的安全区和键盘导航成本最高；实现前需做 960px 宽原型。

### B — 悬浮胶囊式 / Floating Capsule

**可见证据**

- 底部只有一条连续玻璃胶囊；从左到右依次能读出三房间、聊天、唱片/播放、进度、氛围和更多。
- 相框墙仅有一个当前 hover 光圈；聊天卡从粉耳角色方向伸出；氛围面板从胶囊向上展开。
- 设置、装扮、商店被收进右侧更多小面板；右上模块示例卡与中上 presence pill 分离。

**优势**

- 三版中扫描顺序和触达效率最好，用户不需要先理解物件映射，也能完成高频动作。
- 横向分组天然适配不同房间皮肤；房间缩略图比文字列表更有“去别的空间”感。
- 音乐状态被整合在主操作面，播放态最清楚。

**风险与具体修正**

- 胶囊在打开聊天与氛围时占据下半屏较多注意力。实现时只允许一个附属 popover 打开，并在 4 秒无操作后自动收敛。
- 如果高度与图标间距继续增大，会像桌面 dock/任务栏。工程 token 建议：桌面高度 72px，圆角 36px，左右总宽不超过场景宽 68%。
- 三房间 pictogram 与唱片封面都使用圆形/方形图块，需通过分隔线和 selected rim 明确不同信息层级。

### C — 窄 rail 混合式 / Narrow Rail Hybrid

**可见证据**

- 左侧 rail 已在修订稿中收敛为约 56–60px 的视觉主体，按钮单列排列，没有名称、频道或成员列表。
- rail 顶部展开三张场景缩略图；右侧仍有下一房间箭头，兼顾菜单切换与空间导航。
- 聊天卡从 rail 打开，粉耳角色旁另有情境气泡；聊天入口在打开状态仍可见。
- 许愿罐是唯一高亮 hotspot；播放器、氛围面板、presence 与模块卡均为固定位置，不出现拖拽把手。

**优势**

- 系统功能与场景功能职责最清楚：rail 管“应用”，物件管“世界”。
- 入口位置跨书房、棋牌室、植物园都不变，最利于多场景扩展与键盘焦点顺序。
- 与现有极窄玻璃 rail 的工程方向接近，迁移风险比 A 低，同时已彻底删除 Discord 信息架构。

**风险与具体修正**

- rail 仍会比 A 更早进入视线。默认透明度应跟随 mood，未 hover 时图标降到中低对比，当前项才使用蓝色内发光。
- 房间缩略图打开后占据左上窗景。实现时将其限制为 3×80px 卡片，并在选择后立即收起。
- 聊天大卡容易与蓝耳角色发生空间竞争；固定锚点应在 1586px 时位于 rail 右侧、角色下方，在 960px 时切到右下安全区。

## 6. 不确定性与可比性限制

- 三张图使用同一意图和同一参考底图，但 image generation 会重新解释局部场景与角色，因此不能用于逐像素比较材质或角色比例；它们适合比较 UI 骨架、密度与层级。
- 静态 mockup 只能表现“hover 当前态”和“打开态”，无法验证真实 hover 延迟、自动收起、键盘焦点、触屏命中、动效节奏或误触率。
- 所有文字按 brief 使用 blank bars，因此 presence 的真实中文长度、曲名截断和聊天多行内容尚未接受排版压力测试。
- 玻璃对比度目前是视觉检查，不是 WCAG 数值测量；尤其夜晚档需要在实现稿上采样验证。
- C 的 rail 在图像中视觉主体约 56–60px；生成图不等同 CSS 盒模型。实现应将 rail token 明确锁为 `60px`，并把阴影排除在布局宽度外。

## 7. 推荐与下一步

### 推荐架构

1. **默认采用 C**：60px rail 只放聊天、照片、时间线、音乐、模块、商店、设置；不放文本，不放 presence 成员列表。
2. **吸收 B 的分组**：三房间用视觉缩略图；音乐保持独立 now-playing 状态；氛围是一次只开一个的双排 popover。
3. **吸收 A 的空间隐喻**：场景右缘保留“下一房间”箭头；未来可提供一键隐藏 rail 的沉浸模式。
4. **维持双通道聊天**：点击对方角色打开情境聊天；rail 聊天始终可达并承担未读。两者打开同一会话，不创建第二套信息架构。
5. **热点规则写死**：默认不显示常亮圈；鼠标/键盘焦点只高亮当前一个物件；首次引导也只提示一个。
6. **模块不拖拽**：模块管理器只控制显示/隐藏，布局由预设槽位决定；跨房间使用同一槽位系统。

### 建议先验证的工程原型

- 1586×992 与 960px 两档，检查 rail、聊天卡、三房间 popover 是否碰撞角色。
- 夜晚最低亮度，实测 rail icon、blank presence 文案和未读点的像素对比度。
- 一次只打开一个次级面板的状态机：chat / rooms / mood-weather / more。
- 鼠标、键盘与触屏三种路径下的物件 hotspot 命中与 focus ring。
