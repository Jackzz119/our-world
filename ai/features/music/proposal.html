你问的四件事

歌词授权是什么？
歌词是词作者和音乐出版社的作品，有版权。App 要公开给别人看歌词，得向版权方拿许可，一般通过 Musixmatch、LyricFind 这类公司（它们和出版社签了约，按调用或分成收费）。现在自动匹配用的 LRCLIB 是网友整理的免费库，没有授权声明：你们两个人私下用没问题；哪天公开发行，就换成有授权的来源，或者只显示自己导入的歌词。
「响度扫描、指纹匹配要在用户设备上跑，大文件费电」是什么意思？
两件要把整首歌读一遍的活。响度扫描是算出每首歌有多响，让切歌时音量差不多；指纹匹配是听一遍音频算出声纹，去 AcoustID / MusicBrainz 查这是哪首歌、自动补全标签和封面。没有服务器时只能让上传的手机或电脑来算，一首 Hi-Res 要解码几百 MB 的数据，手机会发热耗电。所以这一期只读文件里已有的 ReplayGain 标签，不做扫描和指纹，等以后有 Worker 再在服务器上做。
「播放直接串流原件（签名 URL + Range 请求）」是什么意思？
存音乐的桶是私有的，外人拿不到。播放时 App 先向 Supabase 要一个临时链接（签名 URL，6 小时内有效，带一段只有服务器能验证的签名），播放器拿这个链接去取文件；取的时候用 Range 请求，只要眼下需要的那一段字节：开头一小段先出声，拖到中间就直接从中间取，不用先把整首下载完。全程是原件原样的字节，没有转码，音质等于原件。
CUE 整轨的原理是什么？
很多无损专辑是整张抓成一个大文件，再配一个 .cue 文本，写着每首从第几分几秒几帧开始（CD 的一帧是 1/75 秒，44.1 kHz 下正好 588 个采样）。我们不切文件：整轨只存一份，每首歌在库里是「这个文件的第 X 到第 Y 个采样」。放到一首的终点时，如果下一首正好接着同一个文件，播放器只把标题和进度换过去，声音一刻不停，所以真正无缝（现场专辑、古典乐章之间没有缝）。锁屏也稳：系统看到的始终是一个一直在放的音频流，没有「停止—加载新文件—再开始」这一步，iPhone 最容易在这一步把后台播放掐掉。

第 2 节

音质原则

「保证音质」落到工程上是五条规矩。后面每个方案都按这五条检查，违反任何一条的做法都不进推荐。

1

原件不动

上传的文件逐比特保存，用 SHA-256 校验（FLAC 另验 STREAMINFO 里的 MD5）。改标题、歌词、海报只改数据库，永远不回写文件。

2

无损链路

无损源只做无损到无损的转换（ALAC / APE / WAV → FLAC），转换前后解码出的 PCM 做 MD5 比对，必须完全一致。有损副本只是省流选项，永远不替换原件，也不从有损再转一次有损。

3

默认纯净

默认不做任何处理：不均衡、不限幅、不额外重采样。响度均衡、交叉淡化是可选的「增强」，开启时全程 32 位浮点、预留余量并做峰值保护。

4

如实标注

界面显示来源格式（如 FLAC 24/96）和实际输出（如「系统以 48 kHz 输出」）。网页做不到比特完美，就不说比特完美。

5

可以验证

每一段链路都有能复现的检查方法：哈希、PCM MD5、网络请求里的类型和大小、无缝测试曲、响度对照值。

第 3 节

业界怎么做

对照了网易云、YouTube Music、Apple Music、Spotify、TIDAL 这些大平台，Plexamp、Roon、Doppler 这些以体验或音质出名的播放器，还有 Koel、Navidrome 这些「自己传歌」的开源项目。

产品值得学不学
网易云音乐黑胶播放页就是品牌（多种唱机样式、动态封面）；逐字歌词加人工翻译开关；歌词海报（长按选句、选模板、分享）；一对一「一起听」，进度和切歌同步皮肤市场和评论流；「高清臻音」「沉浸环绕声」「超清母带」这类由算法处理出来的档位
YouTube Music网页上传个人音乐：最多 10 万首，收 FLAC / M4A / MP3 / OGG / WMA，拖进页面任意位置就开始；进度条按住变粗一年几次大改版；免费用户每月只能看 5 次歌词
Apple Music封面是唯一的色彩来源，文字只用黑或白；逐字歌词、对唱左右分、和声、iOS 26 的逐行翻译和发音；「无损 / Hi-Res 无损」两级徽章点开看参数；同步资料库给每首歌标状态（已匹配、已上传、重复、不符合、出错）；玻璃只用在控件层，不盖内容—
Spotify封面下面直接给歌词预览（官方说测试后互动提升）；Jam 显示每首是谁加的；2025 年起 App 内有无损（FLAC 24/44.1），网页仍是 AAC 256接入条款禁止交叉淡化、禁止复刻 Jam，接它时受限
TIDAL 网页版网页里放 FLAC 到 24/192（Shaka + DASH）；两个播放器之间用 250 ms 微淡化代替无缝；响度均衡只调小（ReplayGain 加 4 dB，但不超过原音量）对第三方开发者只给 30 秒试听
Plexamp · RoonPlexamp 用海报里提取的颜色做「烟熏玻璃」底色，每张专辑一个样子；响度均衡、真无缝、Sweet Fades；Roon 用一个彩点概括信号路径，点开看全链路Plexamp 在同一张专辑里也交叉淡化，用户很反感
Doppler · Albums · Marvis本地曲库播放器的设计标杆：界面随音乐变色、扫码用 Wi-Fi 传歌、专辑级进度条、自定义首页分区—
Koel · Funkwhale · Navidrome · beets按文件哈希查重（不看标签）、支持拖文件夹；每个上传文件单独的状态；服务端扫描、转码、ReplayGain；自动匹配给出候选和相似度，由人确认后才写入—

对我们最有用的三条

  • 网页里的无损只能靠自己。大平台里只有 TIDAL、Qobuz 自己的网页播放器放无损，而且不对第三方开放。我们保留原件、直出原件，在网页里就是第一梯队的音质。
  • 音质标注要描述文件，点开看链路。Apple 的两级徽章和 Roon 的信号路径是对的做法；发明更高的档位不是。
  • 两个人的社交只做小事。谁加的歌、回应、送一首歌（Apple 协作歌单、Spotify Jam 的做法），不做评论流和匹配度百分比。

总体架构：谁来干重活

四种搭法的差别在于解析、转码、响度扫描这些重活放在哪里：用户自己的浏览器、一个后台媒体 Worker、一台自托管的音乐服务器，还是整套流媒体分发。下图蓝色是每种方案在现有系统上多出来的部分。

D1

总体架构怎么搭？

A轻量直连先做这个

浏览器的 Web Worker 解析标签、封面、歌词并算哈希；Supabase Storage 存原件；播放直接串流原件（签名 URL + Range 请求）。

  • 不加任何服务器，最快能用；原件直出，音质链路最短
  • 和现有照片墙同一个模式（浏览器处理 + 私有桶 + RLS）
  • 浏览器放不了的格式（Chrome / Firefox 上的 ALAC、APE、DSD、WavPack）只能提示，或在浏览器里慢慢转
  • 响度扫描、指纹匹配要在用户设备上跑，大文件费电
工作量 ≈ 4 周（M0–M6、M8）

B媒体流水线随后加上

在 A 上加一个小容器（FFmpeg 等），上传后在后台做格式归一、响度、指纹、波形和省流副本，完成后回写并通知前端。

  • 什么格式都能收，手机不用干重活
  • 可重放、幂等、有记录，是生产级做法
  • 多一个服务要部署和看管（成本见第 13 节）
  • Supabase Edge Functions 每次请求只有 2 秒 CPU、256 MB 内存，跑不了 FFmpeg，要另找地方跑（每月约 0–5 美元）
工作量 ≈ A + 1 周（M7）

C自托管音乐服务器

让成熟的开源音乐服务器（Navidrome，OpenSubsonic 接口）管曲库、转码、响度和歌词，我们只做界面和上传桥。

  • 扫描、转码、歌词都是现成的；第三方客户端也能连
  • 要一台常开的机器和磁盘；账号是两套，要做桥接
  • 没有网页上传，权限模型和「世界」对不上
工作量 ≈ 2–3 周 + 长期运维

D流媒体级

像 TIDAL、Apple Music：多码率分片 + CDN，播放器用 MSE 拼接。

  • 采样级无缝、弱网自适应、以后可以加 DRM
  • 打包流水线、清单、MSE 播放器全要做；两个人用是大材小用
工作量 ≈ 6–8 周

播放引擎用哪种？

E1纯净直出

<audio> 元素直接播放原件，配合 Media Session 做锁屏控制。

  • 链路最短，手机锁屏与后台最稳，最省电
  • 没有正增益：响度均衡只能调小；iPhone 上网页不能改音量，连调小都做不到
  • 曲间有几十毫秒的空隙，不能交叉淡化、均衡

E2Web Audio 增强

<audio> 接进 Web Audio：响度增益 → 峰值保护 →（均衡）→ 输出；两个播放槽做交叉淡化。

  • 响度均衡可以调大也可以调小，交叉淡化、均衡、频谱都能做
  • 多一段 32 位浮点处理；音频请求必须带 CORS
  • iPhone 要 iOS 17.5 以上并声明播放类音频会话，否则锁屏断播、被静音键静音；Safari 里 MSE / WebM 流接不进来

E3MSE 流式

把音频切成分片，用 MediaSource 自己拼接（YouTube Music、Spotify 网页版的做法）。

  • 采样级无缝，可以按网速切码率
  • 要额外生成分片或 fMP4 重封装；iPhone 只有 ManagedMediaSource（iOS 17.1+）；实现和调试成本最高

E1+E2纯净为主，增强可选推荐

默认纯净直出；设置里可以打开「增强模式」（完整响度均衡、交叉淡化），iPhone 需 iOS 17.5 以上。手机默认纯净，保证锁屏连播。E3 只用在「同专辑无缝」这一件事上，放到 M6 之后。

  • 默认就是最短、最稳的无损链路
  • 两种输出共用一个状态机和队列，切换不打断播放
  • 两套输出都要测

引擎内部怎么设计

状态与队列

  • 一个与框架无关的 Player 类，React 用 useSyncExternalStore 订阅；停靠栏、托盘、锁屏共用一份状态。
  • 状态：空闲 → 加载中 → 播放 ⇄ 暂停；缓冲中；播完 → 下一首；出错 → 恢复。
  • 队列 = 播放来源（专辑、歌单、搜索结果）+ 用户插进来的「下一首播放」+ 历史。随机用洗牌顺序，上一首沿历史往回走；单曲 / 列表循环。
  • 队列和进度可序列化，下一期一起听就是把它同步给对方。

无缝分三档

  • CUE 整轨：同一个文件按采样点切成虚拟分轨，真正无缝，锁屏也稳。这一期就有。
  • 同专辑连播（M6 之后）：Worker 另存一份 FLAC 的 fMP4 重封装（同样的 FLAC 帧，无损），用 MSE 顺序拼接，采样级无缝；iPhone 用 ManagedMediaSource。
  • 其他：剩 30 秒时签好下一首，第二个元素预先缓冲；能改音量的平台用 250 ms 微淡化接上（TIDAL 网页版的做法），iPhone 上接受几十毫秒空隙。

音量与响度

  • 响度均衡默认关（原则 3）。打开后连续播放同一张专辑时按专辑增益，随机播放时按单曲增益，基准是 ReplayGain 2.0 的 −18 LUFS。
  • 「只调小」：用元素音量衰减，不需要 Web Audio（桌面、安卓、iPad），增益取 10^(G/20) 和 1/峰值中较小的那个，保证不削波。
  • 「完整」：可以调大，走增强模式；iPhone 上任何均衡都要走增强。
  • 响度值来自文件标签，缺的由 Worker 用 rsgain 扫描，只存数据库，绝不改音频。

出错时自己恢复

  • 签名 URL 过期或网络中断：重新签名，从当前位置接着放，最多重试 3 次，间隔递增。
  • 解码失败：自动改放无损串流版或副本，并在信号路径里写明。
  • 来电、别的 App 抢占声音：显示「已暂停」，由用户点播放恢复（浏览器不允许自动恢复）。
  • 输出设备：Chrome、Edge、桌面 Firefox、Safari 18.4+ 可以选外接 DAC；安卓上隐藏这个选项。

锁屏、续播、记录

  • Media Session：封面（96 / 256 / 512）、歌名、进度；播放、暂停、上下首、拖动、快进快退都接上，每次拖动都更新位置。
  • 每 5 秒和离开页面时保存队列与进度，重开后停在原处，不自动播放（沿用现在的约定）。
  • 播放满 30 秒记一次播放记录，用于最近播放和以后的年度回顾。
  • 唱片机的灯随节拍呼吸：用 Worker 预先算好的能量曲线按进度驱动，不碰音频链路，纯净模式也能用。

给桌面壳留好接口

  • 现在就把输出抽象成三种：纯净（<audio>）、增强（Web Audio）、原生。
  • Electron 里的原生输出用 libmpv：独占输出（暂停时释放设备）、按曲目切换采样率、ReplayGain、DSD 走 DoP。Feishin、Supersonic 都是这么做的，TIDAL 桌面版也是「同一套界面 + 原生播放器」。
  • 到那时信号路径才能写「比特完美」。
第 6 节 · D3

上传与入库

上传分八步。前四步全在浏览器里完成，不花流量，几百首也能先看清楚再传；中间是断点续传；最后的重活可以交给媒体 Worker。

  1. 选择

    桌面拖进文件或整个文件夹；手机从「文件」App 里选（iPhone 需要 iOS 18.4 以上才能选整个文件夹；「音乐」App 里的歌拿不到，Apple Music 下载的歌也有 DRM）。一次可以几百首。

  2. 解析

    读标题、艺人、专辑、音轨号、年份、时长、编码参数（采样率、位深、码率）、内嵌封面、内嵌歌词、ReplayGain 和 MusicBrainz ID。同名的 .lrc 和 cover.jpg / folder.jpg 自动配对。老 MP3 和 CUE 里的 GBK / Big5 乱码自动识别转码，卡片上标「已修复编码」，可以撤回。

  3. 查重

    流式计算 SHA-256（不把整个文件读进内存）。同一个世界里已经有这个原件，就跳过上传，只提示「曲库里已有」。

  4. 确认

    按专辑分组预览，能改标题、艺人、专辑、海报、歌词，也能整张专辑一起改；上传前就能直接试听本地文件。浏览器放不了的格式在这一步就标出来，不等传完才发现。

  5. 上传

    断点续传：6 MB 一片，3 首并发，可暂停、继续、失败自动重试；进度存在本地数据库里，刷新页面或换了网络也能接着传。手机锁屏时浏览器会挂起上传，回来后自动继续；大批量上传时申请屏幕常亮（iOS 18.4 起支持），并提示先别关页面。蜂窝网络下传大文件前先提醒。

  6. 入库

    传完调用一次入库 RPC，在一个事务里写曲目、文件、歌词、海报。

  7. 后处理（可选）

    Worker 按任务做无损转换、CUE 切轨、响度扫描、指纹匹配补标签、波形、省流副本，回写后通知前端。

  8. 就绪

    唱片落进曲库，马上能放，能加进「我们的歌单」。

各种格式怎么处理

格式浏览器直接放一期（不加 Worker）加上 Worker 以后
FLAC（到 24/192）全部原件直出原件直出；另生成省流副本
MP3 · AAC（M4A）全部原件直出同左
WAV全部（文件大）原件直出整数 PCM 另存 FLAC 串流版（体积约减半，PCM 一致）；浮点 WAV 保持原样
ALAC（M4A）· AIFF只有 SafariSafari 上直出；其他浏览器标「需转换」无损转 FLAC 串流版
Opus · Vorbis（OGG / WebM）Safari 要 17.4 / 18.4 以上原件直出；老 Safari 标注另生成 AAC 副本
APE · WavPack · TAK · TTA都不行标「需转换」；桌面浏览器可用 ffmpeg.wasm 本地转（约为原生速度的 1/25，可选）无损转 FLAC 串流版
DSD（DSF / DFF）都不行标「需转换」转 FLAC 24/176.4（或 24/88.2），标「由 DSD 转换」：DSD 转 PCM 做不到逐比特，原件照样保留
整轨 + CUE取决于音频格式解析 CUE 成虚拟分轨：同一个文件按采样点切（CUE 的 1/75 秒一帧在常见采样率下都是整数个采样点），曲间天然无缝可选切成独立 FLAC，切完所有分轨拼起来的 PCM 必须与整轨一致

每次无损转换都要验证：两边解码后用 ffmpeg -i X -map 0:a -c:a pcm_s32le -f hash -hash md5 - 算哈希，必须完全一致。不加 pcm_s32le 时 FFmpeg 默认转成 16 bit 再算，会把 24 bit 的差异藏掉。

歌词与海报

曲库与数据模型

一首歌拆成三层：文件是你传上来的东西（音频、CUE、.lrc、封面图，按内容哈希存一次，字节不动）；曲目是曲库里的那一行（标题、艺人、歌词、海报，CUE 整轨切出来的多首歌指向同一个文件的不同片段）；播放版本是真正拿去播放的东西（默认就是原件，必要时加无损串流版和省流副本）。改标签只改数据库，原件永远不回写；你手动改过的字段会被锁住，自动匹配不会覆盖。

权限与存储路径

  • 读：曲目所在世界是我的世界，并且 visibility = 'world' 或我是上传者。文件、播放版本、歌词、海报跟随曲目。
  • 写：新增只能以自己为 owner；删除和改可见性只有上传者；歌词、海报、专辑信息两人都能改（记录修改人）。
  • 「我们的歌单」：两人都能加、删、排序；个人歌单只有自己能动。
  • 存储：新建私有桶 music，路径第一段 = world_id 判成员（同 memories）；私有曲目不搬文件，原件能不能读由数据库判断（上传者本人，或文件属于一首对 TA 可见的曲目），切换「仅自己」立即生效。播放一律用签名 URL。

上传、签名与缓存的细节

  • 上传：TUS 断点续传直连 <项目>.storage.supabase.co，分片必须是 6 MB，上传地址最长 24 小时有效；也可以由服务端签一个只能写某个路径的上传令牌（2 小时有效）。

两个人的小事

社交功能只做贴着「两个人」的几件，不做评论流、匹配度百分比、连续打卡这类东西（也违反陪伴设计铁律里的「只做正反馈」）。

  • 谁加的：「我们的歌单」每一行有个小圆点，是加歌那个人的头像颜色。
  • 回应：每人每首歌一个回应（一颗心或一个表情），两个人都点了心就叠成两个圆点，可以筛「我们都喜欢」。
  • 送一首歌：选一首歌、一句歌词、写一句不超过 60 字的话，用现有的金亮信纸送到对方那边，打开从那句歌词开始放。它和唱片角的「为你选一张」是同一个仪式。
  • 在听什么：「TA 在听《雨天的窗边》」只在真的在听时显示，设置里可以开「悄悄听」不公开。

让它显得高级的细节

  • 没有爆音：播放、暂停、拖动时音量在 120–200 ms 里淡入淡出。同一张专辑连续播放不做交叉淡化（Plexamp 的用户最烦这一点），只在随机播放时淡化。
  • 换歌：封套里滑出新唱片；海报从列表行飞到播放页；背景色在 OKLCH 色彩空间里用约 700 ms 过渡到新海报的主色。
  • 流动底色用提取的颜色，不用糊掉的海报：海报上的字和边框糊开会脏（Plexamp 的经验）。底色在低分辨率上画、最多 30 帧，暂停、面板收起、切到后台时停，低动效和「减少透明效果」时静止。
  • 进度条：按住变粗，拇指上方跟一个时间气泡和那个位置的歌词。
  • 滑动切歌：在封套上左右滑，带回弹，下一张封面从边上露出来。
  • 逐字歌词：字的填充边缘带羽化；自己上下翻歌词时暂停跟随，停 3 秒出现「回到当前句」。低动效模式改为整句高亮。

  • 断网：顶部一条细提示「网络不稳，正在重连」，已缓冲的部分照常放。
  • 键盘（桌面）：空格播放暂停，← → 快退快进 10 秒，↑ ↓ 音量，Shift + ← → 上下首，M 静音，/ 搜索，? 看全部快捷键；输入框里不响应。

在线曲库：下一期怎么接

这一期不接，但架构要为它留好位置。调研里最重要的结论有两条：

  • 没有一家主流平台给网页应用无损音频。Spotify 的网页 SDK 约 AAC 256 kbps，Apple Music 的 MusicKit JS 最高 AAC 256 kbps，YouTube 只能嵌一个看得见的有损视频窗，TIDAL 对第三方只放 30 秒试听，Qobuz 只对合作方开放。
  • 大平台的完整播放都要用户自己有会员，音频走它们的加密播放器，不经过我们的音频链路：响度均衡、无缝、均衡器、信号路径在这些来源上都用不了，有的条款还明确禁止交叉淡化。

来源适配器：一个接口接所有来源

播放器不直接认识「网易云」或「本地曲库」，只认识「来源」。每个来源声明自己的能力和条款限制，播放器据此决定能不能做响度均衡、交叉淡化、一起听。「我们的歌单」存的是规范化的曲目（ISRC、MusicBrainz ID、时长），两个人各自解析到自己有权播放的来源。

// src/lib/music/sources.ts
type EngineKind = 'owned' | 'drm-sdk' | 'visible-embed';  // 自己播放 / 平台加密播放器 / 必须可见的视频窗

export interface MusicSource {
  id: 'library' | 'subsonic' | 'jellyfin' | 'apple' | 'spotify' | 'netease';
  caps: {
    playback: 'none' | 'preview' | 'full';
    engine: EngineKind;
    dsp: boolean;             // 能否接进我们的 Web Audio（响度、淡化、均衡）
    maxQuality: { codec: string; lossless: boolean; bitDepth?: number; sampleRateHz?: number };
    lyrics: 'word' | 'line' | 'plain' | 'none';
    policy: { noCrossfade?: boolean; userMustStart?: boolean; listenTogether: 'ok' | 'same-source' | 'forbidden' };
  };
  connect?(): Promise<void>;                              // OAuth，或填自托管服务器地址
  search(q: string): Promise<SourceItem[]>;
  match?(t: CanonicalTrack): Promise<TrackRef[]>;           // 先按 ISRC 跨来源匹配
  getSource(ref: TrackRef, prefs: QualityPrefs): Promise<Playable>;
  lyrics?(ref: TrackRef): Promise<LyricsDoc | null>;
}

export type Playable =
  | { kind: 'url'; url: string; mime: string; lossless: boolean; expiresAt?: number }   // 走我们的链路
  | { kind: 'sdk'; engine: 'musickit' | 'spotify'; uri: string }                       // 平台加密播放
  | { kind: 'embed'; engine: 'youtube'; videoId: string };

同一时刻只有一个引擎在出声；在「自己的链路」和「平台播放器」之间切换会有 0.1–1 秒的空隙。平台来源的音质徽章写「AAC 256 · 平台提供」，不按我们的标准标无损。

一起听怎么做（下一期）

  • 同步什么：队列、当前曲目、播放 / 暂停、位置与对应的服务器时间。走 Supabase Realtime 的私有频道 world:{id}（聊天已经在用同一套）。
  • 时钟对齐：进房时来回 ping 8–16 次，取往返最短的那次估出两端时钟差（NTP 的做法），每 30–60 秒和页面回到前台时重对一次；之后用「参考时间 + 位置」换算本地应在的位置。开始播放时约定 0.4–0.8 秒后的同一时刻起播，两端先缓冲好。
  • 纠偏：每 1–2 秒比一次。偏差小于 40 ms 不管；40 ms 到 1 秒之间用最多 ±3% 的播放速率慢慢追（保持音高，听不出来）；超过 1 秒或卡顿之后直接跳到正确位置。蓝牙耳机另给一个手动延迟补偿。
  • 谁说了算：谁最后操作谁是主导，另一端跟随；对方离开时自动退出一起听，界面上如实显示（只翻译真实状态）。
  • 前提：两人都要能播同一首歌。自己的曲库天然满足，精度能做到几十毫秒。平台来源只能靠跳转纠偏（误差几百毫秒），而且条款不友好：Spotify 禁止复刻「Jam」这类核心功能，Apple 要求每个人自己点开始。所以一起听只做自己的曲库和自托管来源。

在线曲库先接谁？

O1自托管服务器先做这个

写 OpenSubsonic 适配器（Navidrome，随后 Jellyfin）；反过来也把我们的曲库按 OpenSubsonic 接口开放，音流、Symfonium、Amperfy 这些现成客户端就能离线听、上车载。

  • 无损，走我们自己的链路：响度、无缝、信号路径、一起听全都能用
  • 条款干净；Navidrome 已支持逐字歌词和 ReplayGain
  • 要有人常开一台 NAS 或 VPS；国内家宽常没有公网入站

O2官方会员 SDK

Apple Music（MusicKit JS）做官方全曲库：国内外都有服务，要开发者计划（99 美元 / 年）和每人的会员。Spotify 只限私用（开发模式最多 5 人、都要 Premium）。

  • 曲库最全，合法
  • 网页里只有 AAC 256，没有无损；加密音频不经过我们的链路
  • 条款多：Apple 要求从它的 CDN 加载脚本、用户自己点播放；Spotify 禁止交叉淡化和复刻 Jam

O3开放曲库

Jamendo、Audius、Internet Archive、SoundCloud：免费、合规的独立音乐和现场录音，适合做「找新歌」。

  • 不要会员；Internet Archive 有 FLAC 原件
  • 基本没有你们平时听的流行歌

O4国内平台合作

先对网易云 2026 年开放的个人开发者通道做一次技术验证；QQ 音乐、酷狗只对企业合作方开放。

  • 是你们平时真正在听的曲库
  • 开放渠道的版权是官方 App 的子集：实测一位会员收藏的 30 首里有 18 首拿不到播放地址
  • 每个用户要自己注册凭证；企业合作要公司主体和相关资质
推荐「O1 起步，再接一个 O2」。先做自托管适配器，并把自己的曲库开放成 OpenSubsonic（顺带解决离线和车载）；第二步看你们有哪家会员（Q5）：有 Apple Music 就接 MusicKit，在国内且主要听网易云，就先做网易云官方通道的验证。想要无损又想合规，最好的办法是在 Bandcamp、Qobuz 这类商店买无损下载，再传进自己的曲库。
